# Review of Proposal 2 (dialect-defined types), design f79a92e0 — to apply before implementing commits 12-15

BLOCKERS
B1 Table marker can be lost but physical layout would depend on it. PG format_rewritten_table_sql delegates to SQLite and stores text without a marker (postgres/frontend/catalog.rs:149-151); core calls it on every ALTER rewrite (core/vdbe/execute.rs:12048, 12069, 12431) and CREATE with bound sequence names (core/translate/schema.rs:1176, 1358). A MySQL table losing its marker → after reopen INT PRIMARY KEY no longer a rowid alias → id lives only in the rowid, no autoindex → corruption. Need a neutral core marker `/* turso_frontend:<Dialect::name()> */` + canonical SQLite text; core strips/checks it, stores it on BTreeTable (no field today, schema.rs:3749-3766), re-adds on every rewrite. SQLite dialect refuses any turso_frontend: prefix (today hard-codes PG prefix, core/dialect/sqlite/mod.rs:96-103). Every dialect refuses other dialects' markers (PG falls back to SQLite parsing for unknown text, catalog.rs:63-66; registry dialect check is per-process only, dialect/mod.rs:938-965).
B2 Rowid-alias status must be decided from stored SQL alone (dialect code can change between versions; util.rs:1052-1061). Write the storage type into stored text, or make the PK-eligible name map append-only and lock it with a test.
B3 Alias rule unsound: explicit keys go NotNull→MustBeInt (insert.rs:1151-1169, update.rs:825/871, upsert.rs:687/730); alias register holds NULL so ENCODE skips it (insert.rs:755-760, arrays.rs:250-256); generated keys only checked vs i64::MAX (insert.rs:1513-1532) → INT alias NULL insert can give 2147483648. NOT NULL skipped for aliases (insert.rs:1772): MySQL INT PRIMARY KEY without AUTO_INCREMENT must fail 1048. Need ASSIGN+ENCODE on key register before MustBeInt, range check after generation, auto-assign only when dialect marks column auto-generated (MySQL: 0 also generates).

SHOULD-FIX
S1 Type lookup: 63 call sites look up col.ty_str in a global registry (schema.rs:987-1020); date/time/timestamp/json/varchar/smallint/bigint/bool/numeric are built-ins with PG meaning (schema.rs:828-875); INT/INTEGER/TEXT/BLOB/REAL handled as SQLite primitives before lookup (util.rs:175-181, translate/schema.rs:804/829-860, alter.rs:1301-1325, CHECK validator schema.rs:604-613). Dialect tables must resolve names through the dialect map first, once at schema load, stored on Column. Affinity from the mapped type, not type_from_name (today JSON/ENUM/DATETIME get NUMERIC affinity applied on read, columns.rs:83).
S2 ASSIGN placement: emit_custom_type_encode_columns (arrays.rs:209) is shared by INSERT/INSERT..SELECT (insert.rs:4217), UPDATE (update.rs:1741), UPSERT (upsert.rs:772), ALTER COLUMN rewrite (alter.rs:2758), ADD COLUMN defaults (columns.rs:96-135) — but ASSIGN must run earlier: before BEFORE triggers (insert.rs:625-640), before pre-encode TypeCheck (insert.rs:666, update.rs:1605, upsert.rs:743), before key MustBeInt. Virtual generated columns missing (only affinity, gencol.rs:30, columns.rs:76).
S3 CHECK sees stored form (registers encoded in place before CHECK, insert.rs:672-760): numeric(10,2) CHECK(typeof(p)='text') fails; CHECK (p > 0) refused at CREATE "cannot compare numeric with INTEGER" (translate/schema.rs:165-330). Evaluate CHECK on in-memory values; replace CheckExprType with expr_type. Own commit.
S4 Keep ASSIGN (store-only), CAST and implicit comparison conversion separate: MySQL CAST/comparisons are lenient (int_col = 1.5 must not round; tiny_col = 1000, int_col = 'abc' must not error). Room for lenient mode (INSERT IGNORE) and a warnings channel.
S5 Storage details: ast::TypeSize holds ≤2 params (sqlite/parser/src/ast.rs:2198; schema.rs:5216; translate/schema.rs:843) → ENUM/SET lists can't be written. Unsigned > i64::MAX as TEXT sorts wrongly ("10000000000000000000" < "9223372036854775808") → store as 8-byte big-endian BLOB (records sort INTEGER before BLOB, memcmp matches order). Reserve a zero-date value in time storage now. List exact new core storage types with BASE/ENCODE/DECODE/KEY.
S6 Metadata: ExprType::Named must carry the dialect type (name, params, UNSIGNED, ZEROFILL, display width), not only storage; BOOL vs TINYINT(1); views/subqueries/UNION keep the name. ColumnTypeInfo (statement.rs:109-136) lacks params/origin/flags. CREATE TABLE AS SELECT writes non-STRICT text without marker and params (translate/schema.rs:970-1003).
S7 Error kinds: MySQL messages include column name and row number — add at the INSERT/UPDATE site; RAISE inside ENCODE needs a way to state the kind.

Q1 dialect vs core: dialect (ASSIGN + existing): CHAR trailing-space removal, BINARY zero padding, VARCHAR chars vs TEXT/BLOB bytes, YEAR 2-digit/range, BOOL as TINYINT(1), FLOAT 32-bit rounding, fsp rounding, DATETIME/TIMESTAMP ranges, JSON normalisation, collations via existing ICU (collate.rs:51-62). Neutral core: any-length type parameter lists (ENUM/SET), ENUM sort by index (KEY on index, ORDERED), BIT as unsigned, ON UPDATE expression for columns, session time zone for TIMESTAMP (can wait: UTC target), sequence-backed AUTO_INCREMENT on non-rowid-alias columns, LAST_INSERT_ID semantics (first generated value), warnings.
Q2: WITHOUT ROWID / composite PK / DESC flips (schema.rs:5480-5486, 6062-6066) must apply. Laravel default id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY: decide rowid alias over ranged_integer(0, i64::MAX) with documented limit.
Q6 plan: new commit before 12 for the neutral marker (TestDialect dialect/mod.rs:203-300 + copy of tests/integration/database.rs:173-197); commit 12 includes resolve-once-at-load and dialect-names-win (S1); move 15 before 13; 14 after 13 covering B3 with close/reopen, ALTER, VACUUM tests; S3 own commit; Proposal 1's no-connection rule applies only to < and KEY (ASSIGN can be Func::Dialect, precedent dialect/mod.rs:757).

# Asks from the Phase C (MySQL consumer) design — see /tmp/claude-0/-home-user-turso/d15709bb-7f9a-5758-baa6-00ea81e0de51/scratchpad/phase-c-design.md section 1.6. Must be expressible in Proposal 2 (or 4) with NO MySQL-specific core code:
A Dialect functions (Func::Dialect / exec_scalar_function and type FUNCTIONs) must receive each argument's STATIC type (the resolved ExprType incl. params), not just runtime values. 30,300 currently passing vitess specs pass a decimal or big-integer literal into a dialect function; once decimals become typed text, e.g. LOCATE(…, 1.5) would read '1.5' as 1 instead of rounding to 2. Without A the MySQL DECIMAL slice loses more specs than it gains.
B Checked signed 64-bit integer arithmetic that reports overflow as an error kind (PostgreSQL int8 needs the same; MySQL BIGINT overflow → 1690).
C Unsigned add/subtract/multiply signatures must accept one signed operand (MySQL mixes BIGINT UNSIGNED with signed ints).
D Conversion functions (ASSIGN, CAST, implicit) must receive the TARGET type's parameters (DECIMAL precision/scale, ENUM/SET labels, VARCHAR length, fsp).
E (Proposal 4) AVG computed as SUM / COUNT using the dialect's '/' rule (MySQL AVG adds 4 to scale).
F (later) round typed values to their declared scale where they become GROUP BY/DISTINCT keys.
Also: MySQL keeps hidden digits in DECIMAL division (recorded `64 / 77 * 77` = 64.0000) and applies the declared scale only when a value is shown or stored. So result-parameter rules must give a static result type (precision/scale) that reaches column metadata, and the frontend formats output from that metadata. Make sure Proposal 2's result-parameter rules + declared types in metadata (commit 25) carry the static scale for expression results, not only for columns.
